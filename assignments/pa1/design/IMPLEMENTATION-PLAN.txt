PHASE 2 IMPLEMENTED DESIGN

The following design is implemented in thread.c/h, synch.c/h, and intq.c.
The Phase 2 change did not modify the course tests or Phase 1 timer.c.
Phase 3 subsequently integrated timer.c with the new end-of-tick updates.

1. Thread and lock state

Keep thread.priority as the effective priority used by the scheduler.
The following members were added to struct thread:

    int base_priority;
    struct lock *waiting_lock;
    struct list held_locks;
    struct list_elem lock_wait_elem;

The following members were added to struct lock:

    struct list contenders;
    struct list_elem held_elem;

A thread pointer was added to the condition variable's semaphore_elem:

    struct thread *thread;

The existing semaphore.waiters list still holds blocked threads using
thread.elem. A separate lock.contenders list records acquisition attempts
using lock_wait_elem. Keep an attempt registered until its thread actually
acquires the lock, including the interval after it has been unblocked.
This avoids losing a donation when a woken contender has not run yet.
Each lock belongs to its holder's held_locks list through held_elem.
A thread can wait for only one lock at a time, so one lock_wait_elem is
sufficient. No heap allocation is needed for donation records.

2. Selecting runnable threads and synchronization waiters

Keep a single ready_list. Append newly ready and yielding threads at its
tail. At dispatch, scan for the first thread with the greatest CURRENT
priority. Replace the selected candidate only for a strictly greater
priority. This preserves arrival order among equal priorities.

Use the same rule when sema_up selects a blocked semaphore waiter and
when cond_signal selects a condition waiter. A priority change must be
visible at selection time; a saved priority or insertion-time sort is
not sufficient by itself. Selection is O(n), append is O(1).

Read condition waiters through semaphore_elem.thread. The private
semaphore's waiters list may still be empty if cond_signal runs after
the monitor lock is released but before cond_wait reaches sema_down.
Initialize the thread pointer before publishing the condition waiter.
Condition-list access remains protected by the caller's monitor lock.

3. Computing and propagating donation

In priority mode, a thread's effective priority is the maximum of its
base_priority and the effective priorities of contenders for all locks
it currently holds. Donations combine by maximum, not by addition.

When a contender is registered, recompute the holder. If that holder
is waiting on another lock, continue to its holder. Follow at most eight
holder links and stop at a null holder or a repeated thread. Use the
same recomputation rule when relevant priorities decrease, rather than
only propagating increases.

Nested example (base priorities H=50, M=30, L=10):

    H waits for lock A, held by M
    M waits for lock B, held by L

    H (50) --lock A--> M (50) --lock B--> L (50)

If L releases B, its effective priority is recomputed from its base
and any remaining held locks. M still receives H's donation through A.
Releasing one lock must not discard donations belonging to other locks.

4. Acquiring and releasing a lock

Acquisition, in a protected synchronization operation:
- If the lock is unavailable, set waiting_lock and register the attempt
  in lock.contenders before donation propagation and blocking.
- Call sema_down while preserving the atomic registration/ownership
  transition. Sleeping still uses Pintos's semaphore, not polling.
- After success, remove this contender, clear waiting_lock, assign the
  holder, and link the lock into held_locks.
- Recompute the new holder from any remaining contenders, including
  contenders already unblocked but not yet successful.

Release:
- Remove the lock from held_locks and clear its holder.
- Recompute the releasing thread's priority from its remaining locks.
- Increase the lock semaphore and unblock its highest-priority waiter.
- Finish all bookkeeping before checking whether the CPU should yield.

lock_try_acquire performs the same successful ownership bookkeeping.
An unsuccessful try does not register a contender or donate.

5. Priority setters and preemption

thread_set_priority changes base_priority, recomputes effective priority,
and yields if a ready thread now has a higher priority. An outstanding
donation may keep the effective priority above the new base value.
thread_get_priority returns effective priority.

Protect scheduler and donation metadata within short existing-style
synchronization critical sections. An ordinary extra lock is unsuitable
for protecting the scheduler's own atomic priority update: acquiring it
could block and introduce a new donation dependency. Actual waiting
continues to use semaphores and locks.

Do not yield in the middle of updating metadata. Keep thread_unblock
atomic in thread context; callers check preemption after completing
their operation. Audit thread_create, sema_up, lock_release, the priority
setter, and devices/intq.c's direct unblock path. sema_up must increment
its value before a normal-context yield is possible. During an interrupt,
request intr_yield_on_return instead of calling thread_yield. A ready
thread must displace idle even when both priorities are PRI_MIN.

PHASE 3 IMPLEMENTED DESIGN

1. State and arithmetic

Each thread has nice and recent_cpu. load_avg is global. The existing
all_list covers running, ready, and blocked threads. The ready_list still
selects the first highest-priority entry, preserving equal-priority FIFO.

threads/fixed-point.h implements signed 17.14 values in int32_t, with
F = 1 << 14. Multiplication, division, scaling, and rounding intermediates
use int64_t; no floating-point instructions are used.

The initial thread starts with nice=0 and recent_cpu=0. Ordinary threads
created in MLFQS mode inherit both from their creator and receive their
computed priority before being published. Idle is identified explicitly,
kept at PRI_MIN, and excluded from recent_cpu and ready-thread accounting.
Initialization avoids calling thread_current() on the unfinished bootstrap
thread. Parent-state reads and publication to all_list are atomic.

2. Formulas and rounding

The required mathematical formulas are:

    priority = PRI_MAX - recent_cpu / 4 - 2 * nice
    load_avg = (59/60) * load_avg + (1/60) * ready_threads
    recent_cpu = (2 * load_avg) / (2 * load_avg + 1) * recent_cpu + nice

For stored integer values R = recent_cpu and L = load_avg, the code uses:

    priority = ((PRI_MAX - 2 * nice) * 4 * F - R) / (4 * F)
    L = (59 * L + ready_threads * F) / 60
    coefficient = (2 * L * F) / (2 * L + F)
    R = (coefficient * R) / F + nice * F

Use int64_t intermediates in these expressions. Priority converts the
complete expression toward zero and is then clamped to PRI_MIN..PRI_MAX.
For positive in-range results this is the required downward rounding.
The load-average update combines its numerator before a single division,
avoiding separate early truncation of its two terms. recent_cpu may be
negative and is not clamped. Compute coefficient before multiplying by R.

The load-average and recent_cpu getters return their value times 100,
rounded to nearest, with exact halves away from zero. Scale in 64 bits
before adding or subtracting F/2 and dividing by F.

3. Timer interrupt order

thread_tick() begins accounting; timer_interrupt() wakes expired alarms;
thread_tick_end(ticks) performs periodic updates and the final yield check.
The ordering is:

- Increment the global tick count.
- Mark tick_in_progress, clear ready_changed, and account one recent_cpu
  unit to the running non-idle thread.
- Wake every alarm request whose deadline has arrived.
- On each TIMER_FREQ boundary, count ready threads after those wakeups,
  update load_avg, then recompute recent_cpu for every non-idle thread,
  including blocked threads.
- Every fourth global tick, recompute every non-idle thread's priority.
- Check preemption using the completed state and apply the time-slice
  check. Any context switch occurs only after interrupt return.

During an MLFQS timer tick, thread_unblock marks ready_changed instead of
requesting preemption from stale priorities. thread_tick_end decides after
the periodic calculations. Other interrupt wakeups retain the normal
interrupt-return preemption path. tick_in_progress is cleared at the end.
Kernel threads cannot observe partly updated state between these steps.

4. Interfaces, mode selection, and cost

The -mlfqs startup option selects this scheduler. In that mode, thread_create
ignores its explicit priority, thread_set_priority does not change priority,
and thread_get_priority returns the computed value. Lock donation is
bypassed while ordinary semaphore and lock behavior remains available.

thread_set_nice stores a value in -20..20, recomputes the MLFQS priority,
and checks preemption. thread_get_nice returns the stored value. Getters
for shared recent_cpu/load_avg values are atomic against timer updates.
The default mode retains Phase 2 priority scheduling and lock donation.

Append to the ready list on unblock/yield and choose the first current
maximum. The four-tick quantum preserves round-robin order among peers.
The source DESIGNDOC's C2 table uses values after the tick's accounting
and priority updates, before dispatch, with A, B, C initially in that order.

Per-tick accounting is O(1). Alarm wakeups cost O(k+1); periodic updates
visit O(n) threads. Ready-thread selection and relevant preemption checks
scan O(r) entries. An ordinary MLFQS tick with no wakeup and no priority
update avoids that ready-list scan. The complete interrupt is not claimed
to be O(1) on periodic-update or wakeup ticks.
